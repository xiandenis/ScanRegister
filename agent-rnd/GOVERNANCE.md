# 算法研发治理规范

版本：0.1；状态：首批配置，自动执行能力尚未验收。
依据：仓库根目录 Cursor_Algorithm_Product_SDLC_Governance_Design_v1.0.md；仅落实已批准的首批范围。
本规范是工具无关的流程源；Cursor Rules/Skills/Agents 是入口。领域细节继续引用现有字典、专项规则与六维验证 Skill，不复制第二份。

## 优先级与任务边界

遵守运行环境的权限及当前用户明确授权；本规范不授予任何额外权限。项目内流程冲突以本规范为准，专项算法约束可加强要求，不能豁免治理门禁。历史设计、旧 Skill 索引和计划是材料，不能单独证明当前批准。
先读 AGENTS.md、[Skills 索引](SKILLS_INDEX.md)、当前任务记录及相关源码/字典/测试。路径默认相对仓库根；Markdown 链接相对所在文件。
当前已批准的是治理配置合并，不包含业务实现、数据测试、构建、提交、推送、远端设置或发布。不得把此范围限制套用为以后所有任务的永久禁令；每个新任务核实其授权。

## R：治理风险与批准要求

| 风险 | 判据 | 必需要求 |
|---|---|---|
| R0 | 不改变算法语义的文档、注释、机械调整 | 范围审查及适用检查 |
| R1 | 局部低风险修复，不涉及下列 R2/R3 影响 | 针对性测试与回归、正常评审 |
| R2 | 算法行为、目标函数、数据关联、精度/鲁棒性、数值、并行或性能策略变化 | 独立方案评审；实现前人工批准设计和冻结协议；量化验证及独立结果审计 |
| R3 | 高后果机器人安全、碰撞、执行器或关键实时控制变化 | R2 全部要求，加有权限的领域专家批准及适用的仿真/硬件验证 |

先看影响，不按行数、bug/调参/继续等任务名称降级；不确定时采用更严格要求并说明原因。
L0–L3 仅表示现有验证强度，见 [algo-verification](../.cursor/skills/algo-verification/SKILL.md)。R 与 L 分别记录，不按数字对应。R2/R3 的必需证据不能因选择低 L 而豁免；专项回归要求仍有效。

## G0–G6 与退出条件

| 阶段 | 产物及退出条件 |
|---|---|
| G0 接收 | 任务范围、R/L、授权、材料可访问性与缺口明确 |
| G1 定义 | I/O、单位/坐标系、问题、基线、可量化验收及非目标明确 |
| G2 设计 | 数学假设、替代方案、复杂度、退化/失败模式、实验草案可审查 |
| G3 评审 | 独立评审有具体发现、处理结果；R2/R3 设计有可核验人工批准 |
| G4 冻结 | 数据、基线、参数/选参过程、指标/单位/阈值、环境/硬件/线程、重复/种子及失败处理固定且获必要批准 |
| G5 实现 | 仅实施批准范围；实质偏差返回 G2/G3，相关批准失效 |
| G6 验证审计 | 真实日志、退出码、指标和源码/数据版本一致；独立审计及指定负责人验收 |

R0/R1 可裁剪不适用阶段，在任务记录说明理由；不得将 R2/R3 按轻量路径处理。批准不存在或不可核验时，R2/R3 标记 BLOCKED_FOR_IMPLEMENTATION，可继续只读研究、评审材料及方案准备。

## 批准、独立性与冻结

批准必须能核验批准人、决定、范围、设计/协议版本、时间及可信来源。正式 R2/R3 批准应来自仓库托管评审系统或项目负责人认可的审计系统；Markdown 中自填“已批准”、Agent 结论及偏好二次确认不是批准凭证。
方案作者不可担任独立评审者。评审 Agent 只给建议；APPROVED 不代表人工批准。共享模型/材料的评审有独立性局限，高风险结论仍需有权限的人把关。
G4 在正式实现及最终候选评价前完成。结果出现后要改阈值/数据/基线/选参过程，必须保留原结果、记录原因、协议升版并重新批准；不得静默改为 PASS。实质改动后重新核实批准范围并重跑受影响检查。

## 证据和状态

逐项使用 NOT_RUN、PASS、FAIL、BLOCKED、INCONCLUSIVE；阻断实施另用 BLOCKED_FOR_IMPLEMENTATION。
未运行即 NOT_RUN；缺数据/环境为 BLOCKED；运行但不足以下结论为 INCONCLUSIVE。区分断言失败与环境/执行失败。旧 exe、历史日志、编译成功都不能证明当前算法通过。
每项结果记录命令、退出码、时间、源码提交及工作树差异/未跟踪输入哈希、构建与依赖、数据版本/哈希、参数、硬件/线程/精度、原始日志、指标定义、协议和基线版本。不把 dirty 工作树结果绑定为纯 HEAD 结果。
源码或配置变化后，受影响旧证据标记 STALE 并重跑（STALE 为证据有效性标记，不是测试结果）。报告全部失败和覆盖限制，不挑选有利结果。
最终结论：ACCEPTED、CONDITIONALLY_ACCEPTED、REJECTED、INCONCLUSIVE、BLOCKED；只有全部必需条件满足才是 ACCEPTED。流程配置的验收不能替代产品算法验收。

## 写入、合并与发布

一个文件组同时只允许一个写入者；独立评审只读。测试执行者不能改实现、预期、阈值或删失败用例。构建/测试可写产物，必须在任务授权及允许目录内执行；发现代码问题交还实现者。
保留三条长期主线：`main`（Linux）、`windows`（Windows）、`lidarstudio`（LidarStudio 对接，与 `windows` 同级）。目标策略是短分支经 PR、所需评审及必需检查进入对应长期分支；跨主线同步也走目标分支的 PR（默认 `main`↔`windows`、`windows`↔`lidarstudio`）。不得由旧规则的 pull/push 示例推导操作授权。
分支保护、CI、CODEOWNERS、发布权限须在实际平台配置并验证；本批没有配置，状态 NOT_RUN。规则、Subagents 和本地日志不是强制安全边界。不得仅凭配置存在宣称保护已生效。
推送、发布、部署及破坏性操作须有明确授权，并满足适用门禁。回滚本批仅撤销本次配置差异，不重置整个工作树或覆盖用户原有修改。
